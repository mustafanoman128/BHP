Bengaluru Home Price Predictor — Interview Guide

Project by Mustafa  ·  Live: https://bhp-y0gi.onrender.com  ·  GitHub: mustafanoman128/BHP

One-line summary — say this first in any interview

"It's a full-stack ML web app — a scikit-learn Linear Regression model trained on 7,000 Bengaluru property listings, served via a Flask REST API on Gunicorn, with a vanilla JS frontend, deployed on Render with auto-deploy from GitHub. The model hits 85% R² and supports 240 neighbourhoods."

1. Data & Training Notebook

House Price Prediction Project.ipynb

Jupyter Notebook

What it is: An interactive document where Python code, results, and notes all live together. This is where the entire ML pipeline was built.

What it does: Loads the raw CSV → cleans and explores the data → engineers features → trains and compares models → exports the trained model to disk.

Why it matters: This is your proof of work. Any ML engineer will look here to see your thinking and data decisions.

Interview talking points

"I started with 13,320 rows of raw listings and cleaned it down to 7,264 by removing outliers, impossible sqft values, and properties where bathrooms exceeded bedrooms by more than two."

"I compared three algorithms — Linear Regression (R² 0.85), Decision Tree (0.78), and Lasso (0.69) — and chose Linear Regression because it generalised best."

"I used one-hot encoding for 240 location names, which expanded the feature space from 3 to 243 columns."

Bengaluru_House_Data.csv

Raw Dataset

What it is: 13,320 rows of real Bengaluru property listings — location, size, sqft, bathrooms, price.

What it does: Two things: it was the training data for the model, and it's read at server startup to compute the average price per sqft per neighbourhood (powers the area average badge).

Interview talking points

"The CSV does double duty — training data at model-build time, and a live reference for the area average feature at runtime."

"I load it once at startup and cache the stats in memory — no repeated file I/O on each request."

2. Backend — Server/

server.py

Flask App

What it is: The entry point of the backend. Handles all incoming HTTP requests.

What it does: Serves the frontend HTML, exposes /get_location_names (returns 240 neighbourhoods), and /predict_home_price (takes sqft/BHK/bath/location, returns price + context).

Interview talking points

"I used Flask because it's lightweight — two endpoints don't need a full framework like Django."

"Flask also serves the frontend static files, so I only need one process running instead of a separate web server."

"load_saved_artifacts() is called at module level — not inside if __name__ == '__main__' — because Gunicorn imports the module rather than running it as a script. If I'd put it in the wrong place, the model would never load in production."

util.py

ML Logic

What it is: All the ML and data logic, kept separate from the routing in server.py.

What it does: Loads the model and feature metadata, computes location stats from the CSV, runs predictions, and compares a predicted price against the area average.

Interview talking points

"I separated concerns — server.py handles HTTP, util.py handles ML. If I swapped Flask for FastAPI, I wouldn't touch util.py."

"Artifact paths use os.path.abspath(__file__) instead of relative paths — critical on Linux where Gunicorn can be launched from any working directory."

"Linux is case-sensitive — the folder is Artifacts/ with a capital A. On Windows it works either way, which is a subtle bug that only surfaces on deployment."

requirements.txt

Dependencies

What it is: The list of every Python package the project needs.

What it does: Render runs pip install -r requirements.txt at build time to install everything on the server.

Interview talking points

"I kept it minimal — Flask, scikit-learn, pandas, numpy, and Gunicorn. No bloat."

"Gunicorn is in requirements.txt because it's the production web server — you'd never run it locally but Render needs it."

Artifacts/banglore_home_prices_model.pickle

Trained Model

What it is: The trained Linear Regression model, saved to disk as a binary file using Python's pickle library.

What it does: Loaded into memory at startup. Every price prediction is a call to this object's .predict() method.

Interview talking points

"Model serialisation with pickle is standard for scikit-learn. For larger models you'd use ONNX or joblib, but pickle is appropriate here."

"You train once, save, and the server just loads and uses it — no retraining on every restart."

Artifacts/columns.json

Feature Metadata

What it is: A JSON file listing all 243 feature names in the exact order used during training.

What it does: When a prediction comes in, this file ensures the input array is built in the correct column order before being passed to the model.

Interview talking points

"A trained model expects inputs in a specific order. Pass them in the wrong order and you get silently wrong predictions — no error, just garbage output. This file is the contract that prevents that."

"At scale you'd use a feature store or MLflow, but for this project a JSON file is the right level of complexity."

3. Frontend — Client/

app.html

HTML

What it is: The single page the user sees — the whole UI in one file.

What it does: Defines all the structure: the form, the result box, the EMI calculator, the comparison card. Also loads jQuery, Tom Select, and Google Fonts from CDN.

Interview talking points

"It's a single-page app — one HTML file, no page reloads. JavaScript manipulates the DOM to show/hide sections as the user interacts."

app.css

CSS

What it is: All the visual styling.

What it does: Implements the frosted glass card, amber colour scheme, animated bar chart, and responsive breakpoints for tablet and mobile.

Interview talking points

"I used backdrop-filter: blur() for the frosted glass effect — pure CSS, no images."

"On desktop: height: 100vh; overflow: hidden locks the page to one screen. JavaScript adds a has-result class when a result appears, which switches it to overflow: auto — scroll only unlocks when there's something to scroll to."

"All inputs are minimum 16px font-size on mobile to prevent iOS Safari from auto-zooming when the user taps a field."

app.js

JavaScript

What it is: All the frontend behaviour — API calls, DOM updates, calculations.

What it does: Initialises the searchable dropdowns, fires API requests to Flask, renders the result, EMI, area badge, and comparison bar chart.

Interview talking points

"BASE_URL auto-detects the environment: http://127.0.0.1:5000 on localhost, empty string on any other host so all calls become relative URLs. Zero manual changes needed between local and production."

"The bar chart animation uses a setTimeout trick — set widths to 0 when inserting HTML, then after 60ms apply the real widths. This lets the browser paint the zero-width state first so the CSS transition is visible."

"For the location comparison, I fire two API requests in parallel — rather than waiting for the first to finish before starting the second."

4. Deployment

Platform: Render (free tier Web Service — no credit card required)

How it works: Render watches the GitHub repo. Every git push to the main branch triggers an automatic redeploy — installs dependencies, starts Gunicorn, and the new version is live within minutes.

Start command: gunicorn --bind 0.0.0.0:$PORT server:app

Note: Free tier sleeps after 15 minutes of inactivity. First request after sleep takes ~30 seconds to wake up.

Interview talking points

"I chose Render over AWS EC2 because it doesn't require a credit card on the free tier, has built-in GitHub integration for CI/CD, and manages SSL, process management, and scaling — so I could focus on the application code."

"The deployment pipeline is: commit to main → Render detects push → runs pip install → starts Gunicorn → live. That's basic CI/CD."

"Gunicorn is a production-grade WSGI server. Flask's built-in server is single-threaded and not safe for production — Gunicorn handles multiple requests and process management properly."

5. Key Features & How to Explain Them

1. Searchable Location Dropdown

240 Bengaluru neighbourhoods are searchable via Tom Select — a lightweight JavaScript library. The same dropdown is used in the main form and the comparison tool.

2. Price Range (±15%)

Shown as "Likely range: ₹ X – ₹ Y Lakhs." The ±15% accounts for model uncertainty — an honest way to communicate that the number is an estimate, not a guarantee.

3. Price Per Sq Ft

Calculated as (price × 100,000) / sqft, formatted with the Indian number system (en-IN locale). Indian buyers always think in per-sqft terms, so this makes the result immediately comparable to other properties.

4. EMI Calculator

Standard reducing-balance formula. Defaults: 20% down payment, 8.5% interest, 20-year tenure — typical Indian home loan values. Updates live on every keystroke, no button needed.

5. Location Comparison

User picks up to 2 other neighbourhoods. The app fetches prices for all locations in parallel and renders an animated horizontal bar chart sorted by price. The current location is highlighted in amber.

6. Area Average Badge

Compares the predicted price/sqft against the historical average for that neighbourhood, computed from the CSV at startup. Shows ▲ above / ▼ below / ● at par with a percentage. Differences under 3% are treated as "at par" to avoid misleading precision.

7. Common Interview Questions

Why Linear Regression and not something more powerful like XGBoost?

"Linear Regression outperformed both alternatives I tested on this dataset. The features are mostly numeric with one-hot categorical encoding — a relatively clean, linear problem. A more complex model would risk overfitting on 7,000 rows. I'd revisit if I had more data or added non-linear features."

How do you handle a location the model hasn't seen?

"The model uses a column called 'other' for locations not in the training set. Anything unknown maps to that column — it's a standard fallback for one-hot encoded categoricals."

How would you improve the model?

"More recent data, adding features like proximity to tech parks or metro stations, and trying ensemble methods like Random Forest or Gradient Boosting. Also experimenting with log-transforming the price target to reduce the effect of outlier luxury properties."

What would you change about the architecture at scale?

"At higher traffic I'd separate the ML inference into its own microservice, use a proper feature store instead of a JSON file, add a cache layer (Redis) for repeated queries, and run multiple Gunicorn workers behind a load balancer."

What was the hardest bug you fixed?

"A case-sensitivity issue with the Artifacts/ folder. On Windows the path worked fine because Windows is case-insensitive. On Linux (the Render server), the lowercase path failed silently — the model just didn't load. The fix was using os.path.abspath(__file__) to build absolute paths with the exact correct casing."
